# 提示词撰写指南：从要求词到 L 级提示词

> 工作名：**XenoDesign Prompt Authoring Guide**
> 版本：v1.1 · 2026-11-15
> 作用：教 AI（或人）把一组原始"要求词"编译成完整、自包含、可执行的 L 级提示词，并自动设置注释上限。
> 关系：配合 [异星生物设计_主标准.md](异星生物设计_主标准.md) 与 [L0_通用提示词模板.md](L0_通用提示词模板.md) 使用。

---

## 0.0 两个角色（先分清）

- **提示词作者 / prompt author（第三方模型）**：读这份规范，把用户的要求编译成提示词。**它不负责画生物，也不负责完成 L0–L5。**
- **被测模型 / target model**：拿到提示词后画图，输出 SVG + Markdown 文件。

第三方模型不得因为“自己想画”而改题、降难度、减少约束，或替用户完成设计。

## 0.1 30 秒流程

1. 读用户要求；把“最好/尽量/prefer/ideally/best”这类偏好词标成 **B 加分项**，不占硬约束。
2. 分类为 P / F / Q / N，并按 §5 的积分公式算难度；没有 D 时按规则自动定档。
3. **先输出预检（Preflight）**：英中双语，列出每类选了几个、是哪些、难度、L 范围、冲突、随机种子，并问用户是否修改。
4. 用户确认后，输出对照表、约束卡 JSON、完整提示词、校验清单。
5. 提示词里必须要求被测模型**输出成型的 SVG/MD 文件，并按 L 层级分文件夹**。

## 0.2 预检（正式提示词之前，必须做）

预检不是“解释一下”，而是一道确认闸门。用**自然语言英中双语**写，不能只给表格。

```text
## Preflight / 预检

本次选择 / This selection:
- 全局参数 P / Global parameters: {n} 个 — {IDs + names}
- 委托要求 F / Commissions: {n} 个 — {IDs + names}
- 限定约束 Q / Constraints: {n} 个 — {IDs + names}
- 自然约束 N / Natural constraints: {n} 个 — {IDs + names}
- 加分项 B / Bonus: {n} 个 — {IDs + names}

难度 / Difficulty: 约 D{x}（{points} 分；下一档 D{x+1} 还差 {gap} 分）
升级 / Upgrade: 是否要补 {gap} 分到 D{x+1}？/ Do you want to add {gap} points to reach D{x+1}?
任务层级 / Levels: L0–L{?}
冲突审计 / Conflict audit: {none | pairs + tie_break}
随机种子 / Seed: {seed}

如数量、ID、难度或层级有误，请先告诉我；确认后我再生成正式提示词。
If any count, ID, difficulty, or level is wrong, tell me first; I will write the formal prompt after you confirm.
```

示例 / Example：用户只给 `silicon-based` + `no eyes`，没有指定 D。

P1 5 + Q1 5 = **10 分** → **D0**，注释 150 词，默认 L0；下一档 D1 门槛 40，差 30 分（6 个 Q / 3 个 F）。预检会写：当前 D0，是否要补 30 分升到 D1？不补就按 D0 生成。

规则：

- **先停在这里**，等用户说“确认/继续/go”再输出正式提示词。若用户要求“一次给完”，可以输出预检 + 草稿，但必须标明“未确认草稿”。
- 预检必须列出 **P/F/Q/N/B 五类**；用户口语里的“要求”通常对应 F（委托）和 P（全局），“约束”对应 Q，“自然约束”对应 N。
- 预检要写清**够不够下一档**：当前分数、下一档门槛、差多少分、补几个什么类型能到。
- 预检必须做**同级别冲突审计**（§6.2）：直接矛盾 / 不可兼得 / Tension；有直接矛盾必须给 `tie_break`，不能默默选一个。
- 预检必须记录**随机种子**；同一 seed 可复现，不要临时挑“好画”的组合。

## 0.3 一句话

**输入**一组要求词（例如"硅基、岩浆、三个进食口、无眼、无脊椎"）+ 可选难度/层级；
**输出**一份完整提示词、一张约束卡 JSON、一张"要求词 → 约束 ID"对照表，以及符合难度上限的注释规则。

**核心规则**：注释上限随难度增长——

| 难度 | 积分 | 典型约束量 | 注释上限 |
|---|---:|---|---:|
| **D0** | 0–39 | 0–3 条 | **150 词** |
| **D1** | 40–89 | 4–6 条 | **300 词** |
| **D2** | 90–139 | 7–13 条 | **600 词** |
| **D3** | 140–189 | 14–20 条 | **900 词** |
| **D4** | 190–239 | 按积分 | **1,200 词** |
| **D5** | 240–289 | 按积分 | **1,500 词** |
| **Dn** | `40+50*(n-1)` 起 | 按积分 | `300*n` 词 |

上限是"最多"，不是"必须写满"；**按任务计，不按视图计**。D6+ 拆成多张 ≤D5 的卡；L1 的六视图、L4 的完整动画、L5 的骑车，都共用同一个上限。

## 1. 输入与输出

| | 内容 |
|---|---|
| **输入** | 要求词列表（原始短语即可）；可选：难度 D0/D1/…/Dn、层级 L0–L5、优先级覆盖、随机种子 |
| **输出 0** | **Preflight 预检**：P/F/Q/N/B 的数量与 ID、难度、L 范围、冲突、seed；英中双语；问用户是否修改 |
| **输出 A** | 对照表：要求词 → 约束 ID → P/F/Q/N → 怎么查 |
| **输出 B** | 约束卡 JSON：id、difficulty、points、load、priority、constraints、bonus、conflicts、conflict_audit、tension、tie_break、annotation_limit、seed |
| **输出 C** | 完整提示词（可直接粘给被测模型；含文件输出契约） |
| **输出 D** | 校验清单：18 项，逐项过 |

**只有预检确认后**才输出 A–D。除预检、对照表、约束卡、提示词、校验清单外，不写创作建议、不替用户加约束。

**目标模型输出契约**：提示词必须要求被测模型输出**成型的文件**，而不是“描述一下”：

```text
L0/creature.svg
L0/design.md
L1/front.svg ... L1/bottom.svg
L2/section.svg
L3/skeleton.svg
L3/pelt.svg
L4/motion.svg
L5/ride.svg
manifest.md
```

只输出被请求的层级；每层一个文件夹；每个文件给完整内容。聊天界面不能建文件时，用“路径 + 代码块”的形式逐个输出，路径写在代码块前。

## 2. 八步流程

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | **收集**：逐条抄下要求词，不改写 | 原始列表 |
| 2 | **分类**：每条标 P/F/Q/N/B；“最好/尽量”归 B | 带类别的列表 |
| 3 | **规范化**：把模糊词改成可见/可数/可查的表述 | 约束条目 |
| 4 | **计分定难度**：`5P+10F+5Q+10N`，落 D0–Dn，设上限 | points + difficulty + annotation_limit |
| 5 | **冲突审计**：跨类按优先级；同类分 direct/incompatible/tension | 冲突列表/`tie_break` |
| 6 | **预检**：英中双语列数量/ID/难度/L/冲突/seed，问用户是否修改 | Preflight；**停在这里等确认** |
| 7 | **组装**：套 L 级提示词骨架，写入上限和文件契约 | 完整提示词 |
| 8 | **校验**：18 项检查，全部通过才交 | 校验清单 |

## 3. 分类：P / F / Q / N / B

### 3.1 五个问题

对每条要求词，按顺序问：

1. **它是不是一个全局参数**，不规定具体器官/数量？→ **P**
2. **它是不是一个开放目标**，能用多种形状满足？→ **F**
3. **它是不是在定义身体规划/结构类别**（脊椎、足、外骨骼、肺、对称、分节）？→ **N**
4. **剩下的，是不是对可重复部件的精确数量或禁止项**（眼、肢、开口、翅膀），或硬性几何比例（如贯穿空腔 ≥1/3）？→ **Q**
5. **是不是“最好/尽量/最好能/prefer/ideally/best”这类偏好**？→ **B 加分项**；B 不是硬约束，不计分，所有 D 都可以有。

> 分类顺序是 **P → F → N → Q**，不是冲突优先级 **P > F > Q > N**。先问 N，是为了避免把"无脊椎"这种结构规则误判成"0 条脊椎"的数量规则；如果先问 Q，它一定会被"无"字带走。

### 3.2 判定标准

| 类 | 定义 | 通过测试 | 反例 |
|---|---|---|---|
| **P** | 全局参数，不影响器官布局 | 能用一句参数描述；不指向某个部位 | "有三条腿"不是 P |
| **F** | 开放式设计目标 | 可以用多种形态满足；需要说明书指认 | "恰好三个口"不是 F |
| **Q** | 精确数量或禁止项（针对可重复部件），或硬性几何比例 | 可数、可检查"有没有多" | "无脊椎"不是 Q（是 N） |
| **N** | 身体规划/结构类别 | 在剖面/骨骼里可见；影响整体结构 | "三个口"不是 N（是 Q） |
| **B** | 加分项/偏好 | 可有可无、不影响及格、不计分 | "最好没有眼睛"里的“最好”是 B，不是 Q |

### 3.3 例子表

| 要求词 | 类 | 理由 |
|---|---|---|
| silicon-based biochemistry | P | 全局生化参数 |
| body length 2–3 m | P | 全局体型参数 |
| lives in molten rock | F | 栖息地，开放目标 |
| stores heat in a dorsal organ | F | 功能/器官，形态可多种 |
| communicates by vibration | F | 功能，形态可多种 |
| exactly three feeding openings | Q | 精确数量 |
| no eyes | Q | 可数部位的禁止项 |
| no more than four limbs | Q | 数量上限 |
| no wings | Q | 可数附件的禁止项 |
| no vertebrae | N | 身体结构/分类 |
| no feet; moves on a muscular foot | N | 运动结构/身体规划 |
| exoskeleton of mineral plates | N | 外骨骼结构 |
| radial symmetry | N | 身体对称规划 |

**边界案例**：

- "six limbs" → **Q**（数量），不是 N；但"六肢身体规划"可以在说明书里补充。
- "no feet" → **N**（身体规划），不是 Q；它不是一个"脚的数量"，而是"有没有脚"这个结构类别。
- "no wings" → **Q**（附件禁止项）；翅膀是可数附件，不是身体规划。
- "no eyes" → **Q**；眼睛是可数部位。
- "must be scary" → **拒绝**；不可见、不可数、不可查。请作者改成可见特征（如"外露的锯齿状牙齿、无眼"），或删掉。
- "weird skin" → **拒绝/改写**；改成"半透明晶体板 + 矿物接缝"这类可见描述。

### 3.4 一条要求 = 一个 ID

- 复合句要拆："lives in magma and eats rocks" → `F1` + `F2`；
- 重复的合并；同义的去重；
- “最好/尽量/prefer/ideally + 内容”整体归 B，不拆成硬 Q；除非用户另写一条硬约束；
- 不要替作者新增要求；
- 不要丢掉任何一条。

## 4. 规范化：把"词"变成"可查的约束"

### 4.1 五条规则

1. **可见**：外行能在图上指出来；指不出来就改写。
2. **可数**：数量写成"恰好/最多/至少 N"，不要写"几个/若干"。
3. **可查**：说明里能写出"在图上哪个位置"；写不出就说明太虚。
4. **单义**：一个词只表达一件事；"大型硅基捕食者"拆成体型、生化、食性三条。
5. **不改意图**：可以换词，不可以换设定；拿不准就标注 `interpreted: ...`，让作者确认。

### 4.2 改写前后

| 原始要求词 | 改写后 | 类 |
|---|---|---|
| big | body length 2–3 m | P |
| silicon | silicon-based biochemistry; crystal/mineral body | P |
| lives in lava | lives in molten rock | F |
| several mouths | exactly three feeding openings | Q |
| no eyes | no eyes; no eye-like structures | Q |
| no backbone | no vertebrae | N |
| scary | 拒绝；请改成可见特征（如"外露锯齿、无眼"） | — |
| weird skin | translucent crystal plates with mineral seams | F |

> 改写的底线：**只改表达，不改设定**。把"大"改成"2–3 米"可以；把"岩浆"改成"深海"不行。

## 5. 难度：积分制，D0–Dn

难度不再只看“几条”，而是看**约束负载积分**。这让 D3 不再是天花板，也避免“堆几个软要求就自称高难”。

### 5.1 积分公式

```text
points = 5*P + 10*F + 5*Q + 10*N
```

- P 全局参数 = 5 分：一个画布参数，改动成本较低。
- Q 限定约束 = 5 分：数量/禁止/几何比例，可数但只影响局部。
- F 委托要求 = 10 分：开放式设计目标，需要真正做设计决策。
- N 自然约束 = 10 分：身体规划，牵动剖面/骨骼/多视图，按“委托级”计。
- B 加分项 = 0 分：不影响难度，不参与冲突，所有 D 都可以有。

### 5.2 难度档位

| 难度 | 积分 | 典型约束量 | 单卡注释上限 | 说明 |
|---|---:|---|---:|---|
| **D0** | 0–39 | 0–3 条 | **150 词** | 低于 D1 的地板；少量要求默认落这里 |
| **D1** | 40–89 | 4–6 条 | **300 词** | 第一次跑 |
| **D2** | 90–139 | 7–13 条 | **600 词** | 常规评测 |
| **D3** | 140–189 | 14–20 条 | **900 词** | 挑战 |
| **D4** | 190–239 | 按积分 | **1,200 词** | 高难 |
| **D5** | 240–289 | 按积分 | **1,500 词** | 单卡实际上限 |
| **Dn** | `40+50*(n-1)` 起 | 按积分 | `300*n` 词 | n≥1；D6+ 建议拆卡 |

- **D0** 是地板：用户只给 2 个要求、又没有指定 D，默认 D0，注释 150 词；不硬凑成 D1。
- **D1/D2/D3 的标称构成**仍是 1P+2F+3Q / 2P+4F+6Q+1N / 3P+6F+9Q+2N；但**最终以积分落档**。
- **D3 不是最高**：D4、D5、D6… 按同一规律递推；Dn 的门槛是 `40+50*(n-1)`。
- **单卡上限 D5**：D5 已经是 1,500 词；条数按积分，不固定 32。D6+ 不要求一张卡写完，拆成多张 ≤D5 的卡，整组用 campaign 积分记 Dn。
- 注释上限按任务计，不按视图计；L1 六视图、L4 动画、L5 骑车共用同一个上限。

### 5.3 没有指定 D 时怎么定

1. **先算 points**。
2. `points < 40` → **D0**；不发明约束，不升格。
3. `points >= 40` → `Dn = floor((points-40)/50)+1`。
4. 未指定 D 时，预检**一律写出**“当前 Dn；下一档 D(n+1) 差 X 分”，并问是否要升格。如果 `next_threshold - points <= 15`（离下一档很近），明确建议升格：
   > 再加 X 分（例如 2 个 F / 4 个 Q / 1 个 N）就能到 D(n+1)，要不要升格？
   - 用户说不升，就按当前 Dn；
   - 用户说升，只补用户同意的约束，**不要自己编**；
   - 差距很大时只作为可选项，不逼升级。
5. 用户明确指定 D 时：尊重指定，但不要为了凑 D 而新增约束；在预检里同时写 `declared_D` 和 `computed_D`，两者差距大就提醒。

**例子**：用户给 2 个要求、没指定 D → 10 分 → **D0**。

用户给 6 条 D1 标准构成 → 40 分 → **D1**；到 D2 差 50 分，预检只作为可选项提示，不强烈建议。

用户给 13 条 D2 构成 → 90 分 → **D2**。

用户给 20 条 D3 构成 → 140 分 → **D3**。

### 5.4 “200 个限定词”怎么算

- 200 个 Q × 5 = **1,000 分** → D20（D20 门槛 990，D21 门槛 1,040；差 40 分 = 8 个 Q / 4 个 F）。
- 但**一张卡不能有 200 个 Q**：Q 库只有 25 个维度，每个维度每卡只能取一个值；重复维度是直接矛盾，不是加分。
- 正确做法：先合并同维度变体，再拆成多张卡（例如 8 张 ×25 Q，或按主题拆）；campaign 总分记 D20，单卡仍 ≤D5、≤1,500 词。
- 预检要明确写：`valid Q dimensions: 25/25; duplicates dropped: ...; cards needed: ...`。

### 5.5 注释上限

- D0 150；D1 300；D2 600；D3 900；D4 1,200；D5 1,500；Dn `300*n`。
- D6+ 单卡不再加注释；拆卡后每张按自己的 D 取上限。
- 中文按 1.5 倍字数折算：D1 300 词 ≈ 450 字；D2 600 ≈ 900 字；其余同理。
- 上限是“最多”，不是“必须写满”；写不下就压缩，压缩本身是克制测试。

### 5.6 加分项在所有 D 都有效

- **B 加分项不占积分、不参与冲突、不影响及格**；D0–Dn 都可以有。
- 用户自带“最好/尽量/最好能/优先/prefer/ideally/best”这类词，归 **B**，不要当硬约束，也不要用它抬高 D。
- 加分项只在画廊里做标签；没有加分项不扣分。

## 6. 冲突处理

### 6.1 跨类冲突

按 `P > F > Q > N`：默认保留高的、牺牲低的，在提示词里加 `CONFLICT` 指令，并在注释里写清楚。如果两者其实能共存、只是需要解释，按 §6.3 保留两条并写 `RECONCILE`。

### 6.2 同级别冲突：先分三种

"同级别"指同一个组（P/P、F/F、Q/Q、N/N）。不要一律当死题，也不要一律硬解；先分三类：

| 类型 | 判定 | 例子 | 处理 |
|---|---|---|---|
| **直接矛盾** | 同一个维度取了两个不同值 | P-02 碳基 + P-02 硅基；Q-13 无眼 + Q-13 恰好 2 眼；N-01 有脊椎 + N-01 无脊椎 | 二选一；除非卡片明确是"矛盾挑战"，否则不发货 |
| **不可兼得** | 不同维度，但两个目标互斥 | F-01 岩浆 + F-03 冰下；F-09 光合 + F-02 深海 | 二选一，或改写成边界环境；改写后算 Tension |
| **需要解释** | 不同维度，可以共存，但必须说明 | Q-01 4 肢 + Q-02 2 腿；N-01 无脊椎 + N-03 内骨骼；F-20 拟态 + F-25 变色 | 保留两条，写 `RECONCILE:`；算 Tension |

> 处理同级别冲突的目标不是"消灭冲突"，而是"让冲突可解释、可核对"：能二选一就二选一，能共存就写 `RECONCILE`，不能共存就不要发货。

**判定顺序**：

1. 同维度？→ 直接矛盾。
2. 不同维度但互斥？→ 不可兼得。
3. 不同维度但可共存？→ Tension。
4. 不同类？→ 先按 `P > F > Q > N`；低的被牺牲后仍自洽，就牺牲；如果会产生 Tension，就保留并写 `RECONCILE`。

**直接矛盾的唯一例外**：卡片故意考"冲突处理"。这时必须给 `tie_break`：

- `lower_id_wins`：编号小的赢；
- `higher_id_wins`：编号大的赢；
- `more_specific_wins`：更具体的赢；
- `author_choice`：作者指定。

并在提示词里写清楚；不能让被测模型自己猜。

### 6.2.1 用户自带词的冲突审计（必须做）

素材库用“一个维度一个 ID”降低了同维度冲突，但用户自己写的词不受这个保护。两个不同的 Q、两个不同的 N，也完全可能互斥。例如：

- `no limbs`（Q） + `exactly 2 legs`（Q）→ 不可兼得；
- `no feet`（N） + `exactly 2 feet on the ground`（Q）→ 数量/结构打架；
- `no gills`（N） + `exactly 4 gill openings`（Q）→ 同上；
- `bilateral symmetry`（N） + `radial symmetry`（N）→ 直接矛盾。

预检必须逐对检查：

| 检查 | 输出 |
|---|---|
| 同维度不同值？ | `direct` + `tie_break` 或删一条 |
| 不同维度但互斥？ | `incompatible` + 保留哪条/删哪条 |
| 不同维度可共存？ | `tension` + `RECONCILE` |
| 跨类冲突？ | `P > F > Q > N` + `CONFLICT` |

**不允许**“因为是用户写的，就照单全收”；也不允许“默默删掉一条”。冲突必须进预检、进约束卡、进最终注释规则。没有冲突就写 `conflict_audit: none`。

### 6.3 Tension：保留两条，写 RECONCILE

Tension 不是"谁让路"，而是"两条都要，解释怎么共存"。例：

```text
RECONCILE: Q1 (4 limbs) = Q2 (2 legs) + Q3 (2 manipulators). The total is the sum of the parts; no extra limbs.
```

规则：

1. 两条都保留；
2. 在注释里写 `RECONCILE:` 行，说明怎么共存；
3. 提示词里写 `RECONCILE` 格式；
4. 解释不了，就降级为"不可兼得"，二选一。

**不要把 Tension 当死题**：它是 D2/D3 的难点，不是错误。

### 6.4 有意的冲突 / 提示词里怎么写

如果卡片就是要考"冲突处理"，必须满足：

1. 冲突可解释，不是死题；
2. 说明里给出合理的重新解释；
3. 提示词写明 `tie_break`（同类）或 `P > F > Q > N`（跨类）；
4. 注释用 `CONFLICT:` 或 `RECONCILE:`。

提示词模板（无论有没有冲突都建议保留）：

```text
If two constraints seem to conflict:
1. If they can coexist with an explanation, keep both and write a RECONCILE line.
2. If they cannot coexist and are in different groups, follow P > F > Q > N; write a CONFLICT line.
3. If they cannot coexist and are in the same group, follow the stated TIE-BREAK; if none is stated, keep the more specific constraint; write a CONFLICT line.
```

有同类直接矛盾时，在提示词里加一行 `TIE-BREAK: lower_id_wins`（或你选的规则）；没有就不加。

约束卡里的记录方式：

```json
{
  "conflicts": [
    { "pair": ["Q1", "Q2"], "type": "direct", "resolution": "kept Q1; Q2 dropped" }
  ],
  "conflict_audit": [
    { "pair": ["Q1", "Q2"], "type": "direct", "resolution": "kept Q1; Q2 dropped" }
  ],
  "tension": [],
  "tie_break": "more_specific_wins"
}
```

如果有 Tension，把 `tension` 填成 `["T-01"]`，并在 `conflicts` 里加一条 `type: "tension"` 的记录。

## 7. L 级别怎么加（完整提示词块）

L0 用模板；L1–L5 是在 L0 之后**追加**的指令。所有层级：

- 复用同一份 source package；
- 注释上限按难度，不按层级；
- 不重写 L0 的角色、SVG 规则、约束清单、输出格式；
- 完成不了某一层，就交"该层失败"，不要重画一只新生物。

### 7.1 通用 source reuse

```text
Using the same creature as the source, draw ...
Do not redesign the creature.
```

**源包**：`source/creature.svg` + `source/design.md` + 可选 `preview.png`；Manifest 记 `source_mode` 和 `source_hash`。

### 7.2 L1：六视图

```text
Using the same creature as the source, draw six orthographic views:
front, back, left, right, top, bottom.

One SVG per view, named front.svg, back.svg, left.svg, right.svg, top.svg, bottom.svg.
Use the same scale and alignment in every view. No perspective.
Keep every count, pattern, and proportion identical across views.
If a feature is hidden in one view, it still exists in the design; do not delete it.
Do not redesign the creature.
```

| 代号 | 检查 | 失败长什么样 |
|---|---|---|
| V1 | 六个文件齐全 | 少一个方向 |
| V2 | 数量一致 | 正面 3 肢、背面 4 肢 |
| V3 | 比例/对齐一致 | 头突然变大、身体错位 |
| V4 | 花纹/特征一致 | 正面有斑、背面没有 |
| V5 | 与 L0 源一致 | 画成另一只生物 |
| V6 | 遮挡不删除 | 背面看不到的口直接消失 |

### 7.3 L2：剖面

```text
Using the same creature as the source, draw a cutaway or cross-section SVG
(section.svg, same viewBox).

Choose a plane that shows how all feeding openings connect to a shared digestive cavity.
Show the cavity inside the body outline. Show the structural material
(crystal, mineral, bone, or shell).
Do not label the image. Add one line to the note for each internal feature.
Do not redesign the exterior.
```

| 代号 | 检查 | 失败长什么样 |
|---|---|---|
| S1 | 所有开口都连到腔体 | 只画一条通道 |
| S2 | 腔体在外轮廓内 | 器官跑到身体外面 |
| S3 | 材质与 P 一致 | 硅基生物画出血肉 |
| S4 | 无环境矛盾 | 岩浆生物画出鳃/水肺 |
| S5 | 外轮廓与 L0 一致 | 剖面是另一只生物 |

### 7.4 L3：骨骼 + 拓扑皮张

L3 有两个产出，分开画、分开查。**皮张不是剖面，也不是爆炸图**；它是一张连续皮展开后的平面图。

**骨骼**：

```text
Using the same creature as the source, draw skeleton.svg:
the structural frame, with a faint outline of the body.
Keep the same viewBox.

Joints and limbs must align with the exterior.
Keep the same number of limbs, openings, and segments; do not add or remove any.
```

**皮张（拓扑展开）**：

```text
Also draw pelt.svg: the skin removed as ONE continuous piece and unfolded flat,
like a tiger pelt stretched on the ground. Keep the same viewBox.

Show the complete outer surface, the seam/incision lines, and how the pattern
continues across them.

Treat the skin as a single 2D surface with holes: every feeding opening, eye,
limb socket (or sleeve), and tail base must appear as a hole, a boundary, or an
extension in the sheet.

Show the dorsal / ventral / left / right layout and where the seams run.
The sheet must be one connected piece, not several pieces laid side by side.

Do NOT draw a cutaway.
Do NOT draw an exploded view.
Do NOT separate the skin into multiple pieces.
Do NOT change the creature's counts or pattern.
```

**为什么这样写**：

| 措辞 | 防的是什么 |
|---|---|
| `ONE continuous piece` | 防止画成多块皮拼贴 |
| `unfolded flat, like a tiger pelt` | 防止画成剖面/爆炸图 |
| `single 2D surface with holes` | 逼模型做拓扑展开，而不是"去掉皮" |
| `every opening / eye / limb / tail base` | 让孔洞可以逐一核对 |
| `dorsal / ventral / left / right layout` | 逼模型交代展开方向 |
| `pattern continues across seams` | 测花纹连续性，不是画个轮廓 |
| `Do NOT draw a cutaway / exploded view` | 直接拦住把皮张画成剖面/爆炸图的错误 |

| 代号 | 检查 | 失败长什么样 |
|---|---|---|
| K1 | 骨架支撑轮廓 | 骨骼和外形对不上 |
| K2 | 肢体数一致 | 外 4 肢、骨 6 肢 |
| K3 | 开口有支撑 | 口悬空，没有环/管 |
| K4 | 皮张是**一张连续皮** | 画成三四块皮 |
| K5 | 孔洞全部对上 | 少了眼/口/肢/尾根 |
| K6 | 接缝 + 花纹连续 | 花纹在接缝处断开 |
| K7 | 背/腹/左/右布局合理 | 展开方向说不清 |
| K8 | 不是剖面/爆炸图 | 画成切开的内部结构 |

### 7.5 L4：完整动画（跑跳）

```text
Using the same creature as the source, animate a full locomotion cycle:
idle -> run -> jump -> land -> idle.

Output motion.svg: one self-contained animated SVG using SMIL or CSS.
Use the same 512x512 viewBox. Duration: 2-4 seconds. Loop seamlessly.

Keep the anatomy identical in every frame: same limb count, opening count,
pattern, and proportions.
Show weight, contact, anticipation, and follow-through.
No limb teleportation, no sliding feet, no changing counts.

If you cannot animate, output 8-12 frames as frame01.svg ... frame12.svg
and say so in the note.
```

**4 帧故事板不算 L4。** L4 的最低要求是 `motion.svg`，或 8–12 帧降级并在注释里说明；4 帧只够做分镜，不够做动态核算。

| 代号 | 检查 | 失败长什么样 |
|---|---|---|
| M1 | 循环无缝 | 首尾帧跳变 |
| M2 | 数量稳定 | 跑着跑着多一条腿 |
| M3 | 运动顺序合理 | 没有预备/落地，直接平移 |
| M4 | 接触/重量 | 脚在地上滑，跳起来没有弧线 |
| M5 | 特征持续 | 花纹/开口中途消失 |
| M6 | 与源一致 | 动画里是另一只生物 |
| M7 | 降级声明 | 交帧序列但没说明 |

### 7.6 L5（可选）：致敬骑自行车

L5 是彩蛋，不是核心标准，也不是"回到载具题"。它只用于致敬鹈鹕测试；不计入 L0–L4 的必做链路。

```text
Optional capstone. Using the same creature as the source, show it riding a bicycle.
Use the same viewBox.

Draw the bicycle with two wheels, a frame, handlebars, and pedals.
Show the riding relation: the creature is on the bicycle, in contact with the
seat and pedals, not floating beside it.
The bicycle is an object, not a second creature.

Animate a pedaling/balance cycle (ride.svg) or draw one clear scene (ride.svg).
Keep the creature's anatomy and pattern identical to the source.
```

| 代号 | 检查 | 失败长什么样 |
|---|---|---|
| R1 | 自行车结构 | 只有两个圈，没有车架/踏板 |
| R2 | 骑乘关系 | 生物飘在车旁边 |
| R3 | 踩踏/平衡 | 脚不跟踏板，车不倒也不动 |
| R4 | 与源一致 | 换了另一只生物 |
| R5 | 单生物 + 无文字 | 多画一只生物/写标签 |

### 7.7 文件与注释

| 层级 | 文件 | 注释里必须写 |
|---|---|---|
| L0 | `creature.svg` + `design.md` | 每条约束 → 可见/遮挡 |
| L1 | `front/back/left/right/top/bottom.svg` | `Source: L0 <id>` + 六视图一致性 |
| L2 | `section.svg` | 开口连通、腔体、材质 |
| L3 | `skeleton.svg` + `pelt.svg` | `PELT: one continuous sheet; seams...; holes...` |
| L4 | `motion.svg` 或 `frame01–12.svg` | `MOTION: loop Xs; contact...; frames...` |
| L5 | `ride.svg` | `RIDE: bicycle...; contact...`（可选） |

**注释上限仍然按难度**：D0 150 / D1 300 / D2 600 / D3 900 / D4 1,200 / D5 1,500，按任务不按视图。L3/L4 的注释要覆盖新增视图，但不能超上限。

### 7.8 层级检查矩阵

| 层级 | 核心问题 | 一句话判据 |
|---|---|---|
| L1 | 六个方向是不是同一只？ | 数量/比例/花纹跨视图一致 |
| L2 | 内部撑不撑得住外部？ | 所有开口连到腔体，腔体在轮廓内 |
| L3 | 皮张是不是一张连续拓扑面？ | 一张皮、孔洞全、接缝连续、不是剖面 |
| L4 | 动起来还是不是同一只？ | 循环无缝、数量不变、接触/重量对 |
| L5 | 骑车是不是真的骑？ | 车结构完整、身体接触车、不是漂浮 |

### 7.9 目标模型的文件输出契约

提示词必须让被测模型输出**成型的文件**，而不是“描述一下”或“把代码混在一个回答里”。只输出被请求的层级，每层一个文件夹：

```text
L0/
├── creature.svg
└── design.md
L1/
├── front.svg
├── back.svg
├── left.svg
├── right.svg
├── top.svg
└── bottom.svg
L2/
└── section.svg
L3/
├── skeleton.svg
└── pelt.svg
L4/
└── motion.svg
L5/
└── ride.svg
manifest.md
```

- 每个文件必须是**完整可打开**的内容，不是片段；SVG 要能从 `<svg` 到 `</svg>`。
- 每个 `design.md` / 层级 note 必须遵守当前 D 的注释上限。
- `manifest.md` 列出：文件、层级、字数、`Source: L0 <id>`、冲突/`RECONCILE` 行。
- 如果聊天界面不能建文件：逐个输出“路径 + 完整代码块”，路径写在代码块前；不要只给一个大的合并文件。
- L1–L5 必须复用 L0 的同一只生物；重画/换生物要在 note 里标 `source-drift`。

## 8. 提示词骨架

完整提示词必须包含这 9 节（顺序固定）：

1. **角色 + 不要提问**：你是被测模型，不是提示词作者；
2. **产出什么**：按请求的 L 层级输出成套文件（§7.9），每层一个文件夹，不是一段描述；
3. **SVG 规则**：viewBox 512、全身、单生物、无 `<text>`、无外链、无位图、<512 KB；
4. **约束组 + 优先级**：解释 P/F/Q/N，写 `P > F > Q > N`；有同类直接矛盾时写 `TIE-BREAK`；
5. **加分项**：所有 D 都可选，独立、不加分、不影响及格；用户“最好/尽量”类词放这里；
6. **约束清单**：P1…、F1…、Q1…、N1…，逐条；
7. **注释规则**：每条一行、可见/遮挡、`CONFLICT`/`RECONCILE`、`Source:`、**上限 `{{NOTE_LIMIT}}` 词**、不写世界观；
8. **输出形状**：`Lx/` 文件树 + `manifest.md`；聊天界面用“路径 + 完整代码块”；
9. **自检 8 项**：单生物、viewBox、数量、无 text、每条一行、图文一致、不超上限、冲突有解释。

L1–L5 在第 6 节后插入对应视图指令，并保留第 7–9 节。

> 完整措辞直接用 [L0_通用提示词模板.md](L0_通用提示词模板.md) 的 §1；把其中的 `{{NOTE_LIMIT}}` 换成 150/300/600/900/1,200/1,500（D0–D5）即可；D6+ 先拆卡。不要重写一套自己的规则。

## 9. 给 AI 的元提示词（复制即用）

> 这段是给**第三方提示词作者模型**的。它不画图；它负责分类、计分、预检、组装 prompt。

```text
You are a prompt author for XenoDesign, a visual performance test for AI.
You are NOT the target model: do NOT design or draw the creature, and do NOT complete the SVG task.
Your job is to turn the user's requirement words into a complete, self-contained prompt for another model.

INPUT
- Requirement words: {{REQUIREMENTS}}
- Optional declared difficulty: {{D0 | D1 | D2 | ... | Dn | auto}}
- Optional L-level: {{L0 ... L5}} (default L0)
- Optional priority override: {{...}}
- Random seed: {{SEED}} (if absent, choose one and report it)
- Mode: {{interactive | one-shot}} (default interactive)

CONDUCT
- Do not deliberately choose a lower difficulty or an easier combination. Randomly select from the library using the seed; do not optimize for a particular vendor or model.
- Do not invent constraints to fill a difficulty tier. Do not silently drop user constraints.
- If the user says "最好/尽量/最好能/prefer/ideally/best", classify it as Bonus (B), not a hard constraint; bonus is valid at every D and costs 0 points.
- Q dimensions are unique per card: each Q dimension may take only one value. A card cannot contain 200 distinct Q constraints; split into multiple cards if needed.

STEP 0 — CLASSIFY AND SCORE
Classify every requirement as, in this order:
P = global parameter (size, biochemistry, environment)
F = free design commission (habitat, function, organ)
N = body-plan rule (spine, feet, exoskeleton, symmetry, segmentation)
Q = exact count/prohibition of a repeatable part, or a hard geometric ratio
B = bonus / preference ("最好", "prefer", "ideally")
If a requirement is compound, split it; if vague, rewrite it into a visible/countable form and mark "interpreted: ...".
Do not invent or drop any requirement.

Points: P=5, F=10, Q=5, N=10, B=0.
points = 5*P + 10*F + 5*Q + 10*N.

Difficulty:
- points < 40 -> D0, note cap 150.
- points >= 40 -> Dn = floor((points-40)/50)+1.
- Note cap: D0 150; D1 300; D2 600; D3 900; D4 1200; D5 1500; Dn = 300*n for n>=1.
- A single card is capped at D5/1500 words. Above D5, split into multiple cards of <=D5; the campaign keeps the Dn score.
- If no D is declared and points < 40: use D0. Do not upgrade to D1.
- If no D is declared: always report the current Dn and the gap to D(n+1), and ask whether to upgrade. If the gap is <=15 points, recommend adding the gap (e.g. 2 F / 4 Q / 1 N); if it is larger, present it as optional. Never add constraints without consent.
- If the user declares a D that differs from the computed D: report both as declared_D and computed_D; do not pad with invented constraints.
- If Q duplicates a dimension (e.g. two values for the same Q dimension), merge or mark conflict; never count the duplicate as extra points.

STEP 1 — PREFLIGHT (MANDATORY, BEFORE THE FORMAL PROMPT)
Write this in English and Chinese natural language, not just a table. Include:
- counts and IDs for P, F, Q, N, B (with short names);
- points, computed D, declared D (if any), next threshold and gap;
- requested L levels (default L0) and note cap;
- same-class conflict audit: direct / incompatible / tension, with tie_break if needed;
- duplicate Q dimensions or dropped variants;
- random seed.
Then ask:
"如数量、ID、难度或层级有误，请先告诉我；确认后我再生成正式提示词。
If any count, ID, difficulty, or level is wrong, tell me first; I will write the formal prompt after you confirm."

In interactive mode: STOP after the preflight and wait for confirmation.
In one-shot mode: output the preflight first, then mark the prompt "DRAFT — NOT CONFIRMED".

STEP 2 — TRACE
For each requirement, create exactly one constraint with an ID.
Classify each as P/F/Q/N/B; do not count B in points.
If a requirement is compound, split it. If vague, rewrite it and mark "interpreted: ...".

STEP 3 — CONFLICT CHECK
Cross-class: P > F > Q > N; keep the higher, sacrifice the lower, and include a CONFLICT instruction.
Same-class: classify as direct contradiction, incompatible goals, or tension.
- direct contradiction (same dimension): drop one, or define a tie_break; never ship an unresolvable card.
- incompatible goals (different dimensions, mutually exclusive): choose one, or rewrite into a boundary case.
- tension (different dimensions, can coexist): keep both, mark it with a T-id, and include a RECONCILE instruction.
Never ship dead cards like "no limbs + exactly 3 limbs" or "carbon-based + silicon-based".
If the card intentionally includes a direct contradiction, state the tie_break (lower_id_wins / higher_id_wins / more_specific_wins / author_choice).
User-written constraints are not exempt: audit them even when they are not from the library.

STEP 4 — WRITE THE PROMPT
Use exactly these sections:
1. Role and no-questions instruction; the target model is not the prompt author.
2. What to produce: complete files by requested level, one folder per level, plus manifest.md.
3. SVG rules: viewBox 0 0 512 512, full body, side/3-4 view, one creature, no <text>, no external refs, no raster, <512 KB.
4. Constraint groups and priority.
5. Bonus (non-humanoid, non-soft, non-earth, non-cliché): optional at every D, 0 points, not a pass/fail.
6. Constraints: P1..., F1..., Q1..., N1... with exact wording.
7. Design note rules: one line per constraint, visible feature or hidden, no lore; cap = {{NOTE_LIMIT}} words; include CONFLICT / RECONCILE lines when needed.
8. Output contract: L0/creature.svg + L0/design.md; L1/front.svg...; L2/section.svg; L3/skeleton.svg + pelt.svg; L4/motion.svg; L5/ride.svg; manifest.md. Only requested levels. If the interface cannot create files, give path + complete code block for each file.
9. Self-check (8 items): one creature, viewBox, counts, no text, one line per constraint, note vs drawing, note cap, conflicts explained.

For L1-L5, add the view-specific instruction and the source-reuse instruction.
Do not use "be creative" or style instructions; the constraints do the work.

STEP 5 — VALIDATE
Check:
- every requirement has exactly one ID and one line;
- no invented or dropped constraints;
- points, difficulty, and note cap match;
- D0 default applied when points < 40 and no D was declared;
- near-next upgrade question present when gap <= 15;
- bonus items are not counted as hard constraints and are valid at every D;
- same-class conflicts classified (direct / incompatible / tension);
- direct conflicts have a tie_break;
- tension has a RECONCILE instruction;
- prompt is self-contained (defines P/F/Q/N and SVG rules);
- file output contract is present;
- no "be creative" or style instructions.

OUTPUT
A. Preflight (bilingual; stop here in interactive mode).
After confirmation:
B. Traceability table: requirement | ID | class | how to check.
C. Card JSON: id, difficulty, points, load, priority, constraints, bonus, conflicts, conflict_audit, tension, tie_break, annotation_limit, seed.
D. Complete prompt in one text code block, including the file output contract.
E. Validation checklist with pass/fail.

Output only the preflight and A-E. Do not draw the creature.
```

## 10. 完整例子：7 条要求词 → D1 / 300 词

### 10.1 输入

```text
silicon-based
lives in molten rock
stores heat in a dorsal organ
exactly three feeding openings
no eyes
no more than four limbs
no vertebrae
```

### 10.2 对照表

| 要求词 | ID | 类 | 怎么查 |
|---|---|---|---|
| silicon-based | P1 | P | 晶体/矿物材质可见 |
| lives in molten rock | F1 | F | 黑曜石甲/热孔；背景可有岩浆 |
| stores heat in a dorsal organ | F2 | F | 背部热囊/热孔可见 |
| exactly three feeding openings | Q1 | Q | 数出 3 个，无多余口 |
| no eyes | Q2 | Q | 没有眼状结构 |
| no more than four limbs | Q3 | Q | 数出 ≤4 |
| no vertebrae | N1 | N | 剖面/骨骼里没有脊椎柱 |

**计分**：P1 5 + F2×10 20 + Q3×5 15 + N1×10 10 = **50 分** → **D1（40–89）** → **300 词**。这正是“按条数会误判 D2、按积分应落 D1”的例子。

### 10.3 约束卡 JSON

```json
{
  "id": "X-002",
  "difficulty": "D1",
  "points": 50,
  "load": { "P": 1, "F": 2, "Q": 3, "N": 1 },
  "priority": "P>F>Q>N",
  "annotation_limit": 300,
  "constraints": {
    "P1": "silicon-based biochemistry",
    "F1": "lives in molten rock",
    "F2": "stores heat in a visible dorsal organ",
    "Q1": "exactly three feeding openings",
    "Q2": "no eyes",
    "Q3": "no more than four limbs",
    "N1": "no vertebrae"
  },
  "bonus": ["non-humanoid", "non-soft"],
  "conflicts": []
}
```

### 10.4 组装后的提示词（关键段）

```text
=== THE CONSTRAINTS ===

P1: silicon-based biochemistry.
F1: lives in molten rock.
F2: stores heat in a visible dorsal organ.
Q1: exactly three feeding openings.
Q2: no eyes.
Q3: no more than four limbs.
N1: no vertebrae.

=== THE DESIGN NOTE ===

- At most 300 words.
- One line per constraint:
  P1 → the visible feature that shows it
- If a constraint is hidden in this view, say so and where it is.
- If two constraints conflict, add a CONFLICT line.
- Do not write lore.
```

其余小节（角色、SVG 规则、优先级、加分项、输出形状、自检）直接沿用 L0 模板。

### 10.5 合格的注释结构

```text
P1 → translucent crystal limbs with mineral joints.
F1 → dark obsidian plates with glowing seams; the background is a cracked lava field.
F2 → a dorsal sac glows orange and has three heat vents.
Q1 → one central maw and two lateral siphons; exactly three feeding openings.
Q2 → no eyes; the head is a smooth armored dome.
Q3 → four limbs: two walking legs and two small manipulators.
N1 → no vertebrae; the body is supported by a mineral shell, visible in the cross-section.
```

注意：N1 这句在 L0 单视图里可能看不到，应该写 `hidden in this view; see the cross-section`；上面这句是给 L2 的写法。**L0 不要假装看得见。**

## 11. 校验清单（18 项）

- [ ] 每条要求词都有且只有一个 ID
- [ ] 没有新增约束、没有丢要求
- [ ] 复合句已拆、同义已并
- [ ] P/F/Q/N/B 分类正确；“最好/尽量”已归 B
- [ ] 积分算对：`5P+10F+5Q+10N`
- [ ] 难度按积分落 D0–Dn，而不是只按条数
- [ ] 没有指定 D 且分数 <40 时，默认 D0
- [ ] 离下一档 ≤15 分时，预检问了“是否升格”
- [ ] `annotation_limit` 与难度匹配（150/300/600/900/1,200/1,500）
- [ ] 预检是英中双语，含数量/ID/难度/L/冲突/seed，并先于正式提示词
- [ ] 跨类冲突有优先级
- [ ] 同级别冲突已分类（直接矛盾/不可兼得/Tension），用户自带词也审计
- [ ] 直接矛盾已二选一，或写了 `tie_break`
- [ ] Tension 有 `RECONCILE` 指令；D3 至少 1 个，D2 不超过 1 个
- [ ] 提示词自包含（定义了 P/F/Q/N、SVG 规则、输出格式）
- [ ] 注释规则写了上限，且说明"按任务不按视图"
- [ ] 有按 L 层分文件夹的完整文件输出契约（SVG+MD+manifest）
- [ ] L1+ 有 source reuse 指令；没有"要有创意/画好看点"

## 12. 常见错误

| 错误 | 症状 | 修法 |
|---|---|---|
| 把 N 当成 Q | "无脊椎"被写成"0 条脊椎" | 改成 N1，放到身体规划 |
| 把 Q 当成 F | "三个口"写成"有嘴" | 改成 Q1，精确数量 |
| 复合句不拆 | 一条里塞了栖息地 + 食性 | 拆成 F1/F2 |
| 模糊词不规范化 | "很怪""很大" | 改成可见/可数表述，或退回作者 |
| 同类冲突发货 | "无肢 + 恰好三肢" | 退回，删/改一条 |
| 同级别冲突一律当死题 | Tension 被误删 | 先分类；Tension 保留并写 `RECONCILE` |
| 直接矛盾没写 tie_break | 模型自己猜 | 补 `lower_id_wins` / `higher_id_wins` / `more_specific_wins` / `author_choice` |
| Tension 没写 RECONCILE | 注释只说"都满足了" | 加一行解释怎么共存 |
| D3 没有 Tension | 难度名不副实 | D3 至少 1 个 T；D4+ 按积分与 T 预算 |
| 只按条数定 D | 7 条被误判 D2 | 先算积分；7 条可能是 D1 |
| 2 个要求硬凑 D1 | 低于 D0 还标 D1 | 默认 D0，不发明约束 |
| 跳过预检 | 用户没机会改选项 | 先出英中双语 preflight，等确认 |
| 加分项当硬约束 | “最好”被算进 Q | 归 B，0 分，所有 D 可用 |
| 只给一个合并文件 | 没有按 L 分文件夹 | 按 §7.9 输出完整文件树 |
| 注释上限写死 300 | D2 也写 300 | 按难度 150/300/600/900/1,200/1,500 |
| 上限按视图算 | L1 六视图各 600 | 改成每任务 600 |
| 提示词依赖项目上下文 | 只写"按 P/F/Q/N"不解释 | 在提示词里解释四个组 |
| 加了"要有创意" | 结果不可比 | 删掉 |
| L1+ 没写 source reuse | 模型重画一只新生物 | 加"same creature as the source" |
| 注释写成世界观 | 300 词全是历史 | 改成逐条映射 |
| 注释超上限 | 600 词上限写了 800 | 压缩，或拆卡 |
